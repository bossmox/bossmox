BossMox 0.2.0 preview: cluster resilience. Keeping a cluster running through a failure, and hearing about it when something goes wrong.

**Update** with Update now in BossMox, or as root on the Proxmox node that holds the BossMox VM:

```sh
bash -c "$(curl -fsSL https://github.com/bossmox/bossmox/releases/latest/download/update-bossmox.sh)"
```

Each new feature below was tested on a real test cluster, including pulling a cable and powering a node off. Each one also has a written decision record in [docs/adr](https://github.com/bossmox/bossmox/tree/main/docs/adr).

**New: a backup heartbeat link** ([#31](https://github.com/bossmox/bossmox/issues/31), ADR 0035)

Nodes in a cluster keep checking on each other over one network link. If that link has a problem, a healthy node can be treated as lost. When every node has a second network port, BossMox offers to add a second link: Settings → Redundancy, and a dismissable best-practice note in Health check.
- It first checks that every node can reach every other node on the second network. Then it makes the change, and checks that both links are up on every node.
- If anything fails, it puts the old setup back by itself.
- Tested by cutting one node's first link: the cluster stayed together on the second.

**New: keep this guest running** ([#32](https://github.com/bossmox/bossmox/issues/32), ADR 0036)

Proxmox's high availability (HA) starts a guest again on another node when its node fails. Turn it on from a guest's page, or for several guests in Settings → Redundancy.
- Before turning it on, BossMox checks that the guest can run elsewhere: its disks are on shared storage, and the cluster has enough votes.
- It explains what turning it on means. If a node loses contact with the others, it restarts itself (fencing), so the guest isn't running twice. This is also how a guest can end up restarted on another node when it didn't need to be. BossMox warns about the setups that cause that: a heartbeat with only one network, or VM moves sharing that network.
- A guest stuck in HA's error state shows in Health check with a fix button.
- Tested by powering a node off: its HA guest was running on another node about two and a half minutes later.

**New: a tie-breaker for two-node clusters** ([#33](https://github.com/bossmox/bossmox/issues/33), ADR 0037)

A two-node cluster can't tell which node is still healthy when they lose contact with each other, so both stop guests. A small third machine (a QDevice) gives the deciding vote. BossMox shows the two commands to run on that machine, then sets up the nodes and checks the vote is counted.
- Health check warns when the tie-breaker is off.
- Tested on a two-node cluster: with one node off, the other kept running.

**New: alerts** ([#34](https://github.com/bossmox/bossmox/issues/34), ADR 0038)

On a fresh install, Proxmox's own alerts (a failed backup, a fenced node, new updates) go nowhere: they're sent to root's email, which isn't set. BossMox sets up Proxmox's notifications to go somewhere you'll see them: Settings → Alerts, and a best-practice note in Health check until it's done.
- Choices: phone push with ntfy, Discord, Slack, Microsoft Teams, or Gotify. You paste one link or token. Proxmox sends the alerts, so they arrive even when BossMox is down.
- Failures and warnings are always sent. New updates are on by default. Every finished backup is optional.
- **Your link or token isn't kept by BossMox.** It goes over HTTPS to Proxmox, which keeps it in its root-only private settings. It isn't written to BossMox's files, logs or audit lines, and it's never shown again.
- Send a test, then confirm it arrived.
- **Tested end to end:** ntfy (the test, and a real failed-backup alert) and Gotify. **Not yet tried against real channels:** Discord, Slack and Teams. Their messages follow each service's documented format. If one doesn't arrive, please [open an issue](https://github.com/bossmox/bossmox/issues).
- Email alerts are planned for 0.2.1.

**New: gauges**

The overall processor, memory and storage use is shown as gauges on the Health widget and in the Health check window.

**Fixed**

- **One node whose update check failed blocked Update all nodes for every node** ([#73](https://github.com/bossmox/bossmox/issues/73)). That node now sits the run out, and the others update.
- **The desktop could stop updating with no warning when Proxmox answered slowly** ([#70](https://github.com/bossmox/bossmox/issues/70)), for example while a node hung.
- **Setup couldn't finish when the first node was reached by an IPv6 address** ([#71](https://github.com/bossmox/bossmox/issues/71)).
- **Updating BossMox rolled back on a VM set up behind your own proxy over plain HTTP** ([#72](https://github.com/bossmox/bossmox/issues/72)).
- **The Docker image had no writable folder for its state** ([#75](https://github.com/bossmox/bossmox/issues/75)). It has one now, and [running it elsewhere](https://github.com/bossmox/bossmox/blob/main/docs/running-elsewhere.md) shows the volume to add.
- **install.sh:** `--help` printed nothing from the one-line install, and an `--ip` without a prefix length (/24) got past the checks ([#76](https://github.com/bossmox/bossmox/issues/76)).
- **Small fixes in the app** ([#74](https://github.com/bossmox/bossmox/issues/74)):
  - Cancelling Keep free now keeps your VM choices.
  - A failed upload no longer runs its next step.
  - Being signed out mid-save goes to the sign-in screen.

**Under the hood**

- **A code formatter, and a checker for the install and update scripts, run on every change** ([#62](https://github.com/bossmox/bossmox/issues/62)).
