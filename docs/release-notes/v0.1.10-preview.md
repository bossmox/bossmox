BossMox 0.1.10 preview: security fixes from the second review, and Update all nodes no longer stalls.

**Update** with Update now in BossMox, or as root on the Proxmox node that holds the BossMox VM:

```sh
bash -c "$(curl -fsSL https://github.com/bossmox/bossmox/releases/latest/download/update-bossmox.sh)"
```

This is the first release that's a patch. From here, fixes to a released version bump the last number (0.2.0 to 0.2.1), and new features bump the middle one. The cluster resilience work on the [roadmap](https://github.com/bossmox/bossmox/blob/main/ROADMAP.md) is now 0.2.0.

**Fixed: Update all nodes stalled after the first node**

Seen on a real cluster: the first node's updates installed in seconds, then the run sat at "installing". The install printed its log in the node's console, the console paged it, and the pager waited for a key nobody pressed. Every node would have waited out the 45-minute limit. Commands BossMox types into a node's console no longer page. If a run is stuck like this on 0.1.9, pressing q in that node's Shell lets it carry on.

**Security fixes**

These were in [SECURITY.md](https://github.com/bossmox/bossmox/blob/main/SECURITY.md)'s scope, found by the second outside review of 0.1.9.

- **Wipe disk and storage deletes could miss a guest hidden from your account.** Before erasing, BossMox checks that your account sees every guest. A No access set on one VM or on a pool slipped past that check. It's counted now.
- **Other people's usernames showed to accounts that couldn't change the cluster:** in the list of guests moved away, in a run's Stop note, and in the message refusing to stop someone else's run.
- **During setup, a sign-in still waiting on Proxmox when someone entered the setup code again** could land afterwards with its password. It's refused now.

Details: [ADR 0034](https://github.com/bossmox/bossmox/blob/main/docs/adr/0034-security-patch.md).
