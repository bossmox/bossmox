BossMox 0.3.0 preview: upgrade your cluster from Proxmox VE 8 to 9, one node at a time, from the browser.

**Update** with Update now in BossMox, or as root on the Proxmox node that holds the BossMox VM:

```sh
bash -c "$(curl -fsSL https://github.com/bossmox/bossmox/releases/latest/download/update-bossmox.sh)"
```

Proxmox VE 8 stopped getting updates on 2026-08-31. This release is about getting off it safely. Each piece below was tested on real test clusters, and the design is written up in [ADR 0042](https://github.com/bossmox/bossmox/blob/main/docs/adr/0042-proxmox-upgrades.md).

**Before you start:** have recent backups of your guests. BossMox moves them off each node before upgrading it, but a major upgrade is still a major upgrade.

**New: Proxmox's own end-of-life dates, where you'll see them** ([#95](https://github.com/bossmox/bossmox/issues/95))

- Health check has a line for each Proxmox version in your cluster: fine, a warning six months before updates end, and a problem once they have. The dates come from Proxmox's FAQ, kept in BossMox and refreshed with each release.
- The top bar shows a notice when a node runs a version that no longer gets updates (red, opens Health check), or when updates are waiting (amber, opens Update all nodes).

**New: Get ready to upgrade** (Health check → the end-of-life line)

BossMox runs Proxmox's own upgrade checker (`pve8to9 --full`) on every node, one at a time, and explains each finding in plain words: what it means, and whether BossMox deals with it, you need to fix it first, or it's just good to know. Proxmox's own wording is one click away. It also checks free space on each node's root disk, PCI passthrough and storage plugins Proxmox doesn't ship. The checker only reads; nothing changes on the nodes. Needs root@pam.

Only findings that really stop an upgrade hold it back. For example, the Proxmox 9 checker reports a failure on every virtual machine for a missing processor microcode package; BossMox explains it and carries on.

**New: fixes that keep a node reachable after the upgrade**

- **Port names are pinned** before each node restarts, with Proxmox's `pve-network-interface-pinning`, so a new kernel can't rename a network port and cut the node off. BossMox leaves alone ports that another file already names (cloud-init does this), checks with udev that each pin will take, and takes its pins back out if one wouldn't. You can also pin from the window ahead of time.
- **Shared LVM:** a button runs Proxmox's autoactivation migration on each node, which Proxmox strongly recommends before going to 9.
- **GRUB on UEFI with LVM, the `systemd-boot` package, and old `/etc/sysctl.conf` settings:** BossMox finds them and shows Proxmox's command for each. It doesn't run these for you yet.

**New: Upgrade all nodes**

Once the check finds nothing in the way, the upgrade window has **Upgrade all nodes**. It opens the same plan screen as Update all nodes: for each running guest you choose Move or Shut down. Then BossMox goes one node at a time:

1. moves its guests to other nodes, or shuts them down,
2. switches the node's Debian and Proxmox update sources to the new release (after a backup; if apt doesn't take the new sources cleanly, the old ones go back),
3. runs Proxmox's checker, installs Proxmox VE 9 unattended, and checks again,
4. pins the port names and restarts the node,
5. checks it came back on 9 with the new kernel, then starts what it shut down and brings the rest home.

- Guests never move from a node on 9 to one still on 8.
- BossMox can move itself off a node like any other guest, and the run carries on.
- Each node took about 15 minutes on the test clusters. Allow 10 to 30.
- **Stop** lets the node under way finish its upgrade and start what it shut down, then ends the run. Guests it moved stay where they are; Move everything back on a node's Overview brings them home. Start Upgrade all nodes again to do the rest.
- Config files you changed keep your version. Proxmox's new one sits beside each as `.dpkg-dist`, and the run lists them per node.
- A node left halfway (version 9 packages installed, still running 8's kernel) is found and finished without installing again.
- It refuses to start, and says why, unless: you're signed in as root@pam, the cluster is quorate with every node online, and the readiness check ran within the last hour and found nothing in the way.

You can also do a single node from its line in the upgrade window: switch its sources (with a way back), then upgrade it. That needs the node empty of running guests, 5 GB free on root, and 90 minutes left on your sign-in.

**Tested**

- A three-node cluster with an HA guest and shared LVM over iSCSI, from 8.4.21 to 9.2.28, entirely from the browser, including pressing Stop part way and finishing with a second run. Port names pinned, heartbeat addresses kept, quorate throughout.
- A two-node cluster with a tie-breaker vote, from 8.4.21 to 9.2.28 in one run. The vote kept quorum while each node restarted.
- A cluster with one node already on 9 and the others on 8.

**Not tested yet**

The test clusters are virtual machines, so these weren't shown:
- Real hardware, where port renames actually happen. Pinning was tested, but the lab's ports would not have been renamed anyway.
- Booting UEFI from LVM, and PCI passthrough.
- **Ceph.** BossMox doesn't upgrade Ceph. Proxmox's checker reports Ceph below Squid 19.2 as a failure, and BossMox stops on any failure it doesn't know to be harmless. Upgrade Ceph in Proxmox's interface first. No Ceph cluster was tried.
- A second heartbeat (corosync) link during the upgrade.
- HA groups, which Proxmox 9 turns into HA rules.

**Known**

- The readiness check's results are kept in memory, so a BossMox restart clears them. Running it again takes seconds.
